Tokenizer / BPE

全站每一页都从 token 起步：KV Cache 按 token 记账、采样在词表上出分布、你按 token 付费 —— 但 token 到底是什么？为什么模型数不清 strawberry 里有几个 r？为什么中文比英文贵？点六次按钮，看 BPE 怎么把字符滚成词表。

LAYER 1

strawberry 之谜：模型看不见字母

本层目标：理解 token ≠ 字符 ≠ 词 —— 模型阅读的是另一种单位。

图 1 · 同一个单词，两种视角

cl100k 分词器把 strawberry 切成 [str][aw][berry] 三个 token —— 三个 r 分别藏在第 1 和第 3 个 token 内部。模型要数 r，必须「反编译」每个 token 回字符 —— 这不是智力问题，是输入格式问题。同理：数字运算按位切、代码缩进被合并，都是分词器的锅。

认知检查 · LAYER 1

以下哪个说法是对的？

「the」是一个 token（高频），「theoretical」可能是 [the][oret][ical]（低频词被拆）。切法完全由词表统计决定，没有语言学规则。
LAYER 2

BPE：高频字符对的滚雪球

本层目标：亲手点六次合并，看词表怎么从 7 个字符长出来。

图 2 · BPE 合并动画（语料：low low low lower lowest）

每一步：数所有相邻对频次 → 合并最高的 → 写进词表。l+o 出现 5 次先合并成 lo，lo+w 又是 5 次成 low，然后 low+e（2 次）…… 频次逐级衰减是常态 —— 高频词滚成整词 token，低频词留给字符组合。语料总 token 从 22 降到 7：压缩就是分词的全部目的。

词表 = 初始字节/字符集 + N 次合并规则 · 解码新文本 = 按词表贪心匹配 真实 BPE 在数 GB 语料上做 5~12 万次合并；GPT-4o 之后再训练的 tokenizer 用同样的思想加了正则预切分（不跨单词/数字边界合并）
认知检查 · LAYER 2

为什么 "lowest" 在动画里最后才整体成为 token，而 "low" 很早就成了？

在真实词表里 lowest 通常也不是完整 token —— 出现太少。BPE 的世界只认频次，不认语义。
LAYER 3

词表演进：15 → 18 bits 的军备竞赛

本层目标：看懂词表大小背后的三笔账 —— bits、效率、成本。

图 3 · 词表演进与每 token 信息量

词表越大 → 高频组合（含中文词、代码惯用语）越可能整体成 token → 同样内容 token 数越少 → 上下文更耐用、推理更便宜（回忆 KV Cache 页：每 token 都有显存账单）。代价：embedding 矩阵更大（128k × 4096 × 2B ≈ 1GB）+ softmax 计算变贵。Llama-3 的 17.0 bits 正是 Mostik 页「每 token 17 bits」的出处。

认知检查 · LAYER 3

词表从 32k 扩到 128k，同一篇文章的 token 数会怎么变？

中文受益最明显：旧词表每汉字 1-2 token，大词表常见词组成单 token —— 这就是 Qwen/Gemma 把词表做到 15-25 万的动机：中文用户同样的窗口装下更多内容。
LAYER 4

中英效率：同样的窗口，不同的容量

本层目标：算清「中文为什么贵」这笔账。

图 4 · 同信息量的 token 账单对比

同样 100 单位内容：英文 100 词 ≈ 150 token，中文 100 汉字（新 tokenizer）≈ 67 token —— 但旧 GPT-3.5 时代要 133 token（每汉字 1.33 个）。中文「贵」是词表偏英文的历史问题，不是语言本身的问题；国产大词表模型已把这笔钱省了。emoji 更惨：UTF-8 四字节被切碎，一个 😀 旧价 3-4 token。

认知检查 · LAYER 4

128k 窗口的模型，中英文各能装多少内容？

128k × 1.5 汉字/token = 19.2 万字。汉字单字信息量高于英文单词的 1/1.5，所以同窗口中文装的内容确实更多 —— 前提是 tokenizer 对中文友好。
LAYER 5

落地：上下文换算器 + 分词器的锅

本层目标：建立 token ↔ 页/书的直觉，并记住分词器背的锅清单。

图 5 · 上下文换算器（点按钮切换中英文）

128k ≈ 一本长篇小说或两本中文中篇 —— 所谓「长上下文」就是让你把整个代码库或十几份 PDF 塞进一次对话。1M（Gemini）≈ 10 本书。

现象分词器的锅
数不清 strawberry 的 r / 拼写错误r 藏在 token 内部，模型不直接看字符（L1）
大数算术错（123×456）数字按 3 位一切（[123][456]），进位模式学不到
代码缩进/空格敏感 bug连续空格被合并成专用 token，缩进语义漂移
反向拼写 / 首字母任务差token 顺序是模型看到的全部 —— 字符序不在输入里
提示词注入难防「忽略以上指令」和变体可能被切成不同 token —— 规则匹配漏网

带走的五句话

  • 模型看的是 token 不是字符 —— strawberry 的 r 藏在 token 内部（L1）
  • BPE = 高频字符对贪心合并：高频词滚成整 token，低频词留字符组合（L2）
  • 词表 5 万→25 万：log2 = 15-18 bits/token，Mostik 的「17 bits」就是 Llama-3 词表（L3）
  • 中文曾贵 1.3 倍是词表偏英文的历史账，大词表（Qwen 15 万）已纠正（L4）
  • 128k ≈ 一本长篇/19 万汉字；数数/算术/缩进 bug 多半是分词器的锅（L5）

术语速查

token
词表中的一个条目 —— 词、词片、字符或字节。模型世界的基本单位。
BPE (Byte Pair Encoding)
从字符开始反复合并最高频相邻对的算法 —— 现代分词器的骨架。
byte-level BPE
以 256 个字节为初始词表 —— 任何 UTF-8 文本都永不 OOV（未知字符有 fallback）。
OOV (out-of-vocabulary)
词表里没有的序列。byte-level BPE 后基本消灭 —— 代价是切成更多 token。
特殊 token
<|im_start|>、</s> 等 chat template 专用标记 —— 不在文本统计里，是设计出来的。
tiktoken
OpenAI 的分词器库 —— 网页版 tiktokenizer 可实测任意文本的 token 数。
